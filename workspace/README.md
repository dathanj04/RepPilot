# RepPilot workspace
Private hosted outreach workspace, upgraded from the static demo. Practices, visits, tasks, ordered routes, lunches, monthly focus, aggregate referral entries, and settings persist as a versioned workspace JSON file in the BUCKET R2 binding. Records are scoped to platform authenticated user IDs. Conditional writes detect conflicts between tabs; failed saves remain visible and prevent accidental page closing. The owner-only Site audience is preserved.

20 clinic records are carried forward from the supplied directory. Fictional activity and sample practices are not used to initialize the workspace. The old demo browser storage is left untouched and is not automatically imported.

Run `node scripts/build.mjs` and `node scripts/test.mjs`. The preview uses memory storage with a preview identity; hosted storage uses R2 and trusted platform identity headers.

Includes practice CRUD editing/addition, CSV import with duplicate detection, visit history and notes-based next conversation briefs, follow-up completion, route reordering and Google Maps destination links, lunch scheduling/confirmation, ICS event downloads, real activity reports, CSV visit export, complete JSON backup download, and workspace settings.

Not configured: Salesforce/HubSpot sync, external AI generation, calendar OAuth sync, public practice self-scheduling, billing, team invitations/roles, food ordering APIs or app-store submission. UI reports these connection limits. No patient information should be entered. Existing Grok production deployment is separate and was not modified.

## Practice map dots
All 20 supplied clinic addresses have sourced coordinates: 18 US Census address-range matches, one shopping-center coordinate from its leasing brochure (suite approximate), and one OpenStreetMap clinic-building coordinate. Existing saved workspaces receive coordinates only where the directory ID and address still match and coordinates are missing. User edits, visits, and existing coordinates are preserved. Dot tooltips show name and address.

## Provider scheduling
Provider scheduling uses a separate scheduling/v1.json R2 document with conditional writes. Rep routes require authenticated platform identity and filter by owner. Practice links are unguessable bearer capabilities; only their offered availability and own request status appear publicly. A separate public portal proxies only token-scoped provider operations to this private Site using its runtime service credential. No workspace data or credentials are returned by the portal. Links can be revoked; direct booking is allowed once within 24 hours, then approval required. Representatives explicitly offer hour-separated slots; external-calendar conflicts are not checked. Confirmed requests project into the RepPilot lunch calendar. ICS downloads retain request-based event UIDs. Email updates use explicit mailto drafts; no automatic mail or external-calendar sync is claimed.

## Excel/CSV accounts, exports, and manager assignments
Import & export supports XLSX with worksheet selection and CSV; files are parsed locally, mapped, previewed, validated and deduplicated before commit. Imports are limited to 2,000 rows and 5 MB; XLSX uncompressed archive size is bounded. CSV and Excel account/activity downloads include account IDs, coordinates, assignments and CRM identifiers. Formula injection is escaped in CSV; Excel values are written as data cells. Activity date filters apply only to activity, not account records. Browser Excel support uses the bundled ExcelJS 4.4.0 with MIT license.

/api/team uses a canonical shared account document with conditional writes. TEAM_MANAGER_EMAIL identifies the sole manager by the platform-authenticated email header. Roster members are matched by their sign-in email; only assigned accounts are returned, and server checks prevent reps from changing ownership or other reps' accounts. Reps can add their own accounts through imports. Site access remains owner-private until the owner explicitly grants members access; creating roster records does not change site permissions. First manager load seeds the shared directory from their existing workspace without removing the personal workspace.

Missing US address coordinates can be looked up using /api/geocode against the US Census address-range geocoder. Results are cached and approximate. Failed or unmatched lookups remain for manual address review; user-provided coordinate pairs are retained.

CRM preview readers support HubSpot companies and Salesforce Account records with pagination, error handling and manager-only access. They are inactive until runtime secrets HUBSPOT_ACCESS_TOKEN, or SALESFORCE_ACCESS_TOKEN plus SALESFORCE_INSTANCE_URL, are configured; no credentials are embedded in browser source or hosting manifests. CRM imports do not write back. Existing live connections were not available for testing. CRM CSV/XLSX exports work now. Rep activity exports contain the signed-in user's activity; cross-rep activity rollups are not implemented.

## Route optimization
Route planner supports choosing a starting account, open routes, a fixed finishing account, and return-to-start routes. The default optimizer runs entirely in the browser on great-circle distances (Haversine). It supports up to 120 selected stops, finds an exact best order for up to 11 intermediate stops, and uses multi-start nearest-neighbor plus directed segment-reversal improvements for larger routes. It retains the original order when no shorter candidate is found. Results are previewed before application; apply, undo, numbered map stops, CSV export, coordinate-change invalidation, and workspace persistence are implemented.

Map-distance results are explicitly straight-line estimates, not driving miles or times. Browser QA verified preview, apply, and persistence after reload with three public directory clinic stops. Synthetic tests verify fixed endpoints, round trips, directed costs, missing locations, 120-stop completeness, and optimality against exhaustive permutations for small cases.

A road-time path is prepared at /api/routing but disabled until runtime ROUTE_PROVIDER_APPROVED=true is explicitly authorized. Automatic approval review rejected the initial routing-service test because sending practice coordinates externally lacked specific approval. Do not enable or test live requests without that approval. If enabled later, the endpoint sends only coordinates to the configured HTTPS OSRM_ROUTING_URL (default https://router.project-osrm.org), caps road requests at 25 stops, caches results for 24 hours, and limits uncached shared-provider requests to one per 1.1 seconds. No live traffic or appointment windows are used. Road API and cache behavior have only been tested using mocked responses with synthetic coordinates; real provider connectivity has not been verified. A dedicated routing provider is recommended before high-volume use.

### Road routing enabled
The owner approved road routing on November 9, 2026 in response to the explicit coordinate-sharing question. ROUTE_PROVIDER_APPROVED=true and OSRM_ROUTING_URL=https://router.project-osrm.org are configured as runtime values. The app selects driving-time optimization by default when the status endpoint confirms enablement. A live authorized test returned a two-clinic Dallas round trip of approximately 15.6 road miles, 29.5 minutes, two legs and 26 geometry points. This verifies provider connectivity as well as optimizer output; travel estimates do not incorporate live traffic. The earlier disabled-state notes above document the original implementation and are superseded by this approval.
